    Testy i pakiet

    Masz już modele prognozy. Teraz napiszesz testy, które pozwolą sprawdzić ich działanie po kolejnych zmianach. Przygotujesz też pakiet, który można zainstalować poza folderem kursu.

    • Czas: około 60 minut
    • Wymagane: moduły 01-03
    • Potem: lab 04 i punkt kontrolny 1, około 6 godzin

    Po tym wykładzie będziesz umiał:

    • powiedzieć, co test modelu prognozy sprawdza, a czego nie,
    • pisać testy w pytest: asercje, błędy, liczby zmiennoprzecinkowe, parametryzację, fixtures,
    • odciąć test od sieci, daty i innych zależności: przez parametr, monkeypatch albo Mock,
    • ocenić, czy test coś chroni, zanim zaufasz mu przy zmianie kodu,
    • czytać pyproject.toml i uv.lock i wiedzieć, co robi uv sync,
    • wyjaśnić, po co układ src/ i instalacja edytowalna.

    Co testujesz w modelu prognozy

    Model z labu 03 działa w dwóch krokach: fit zapamiętuje historię, a predict zwraca prognozę na zadany horyzont. Docstring określa szczegóły tego działania, na przykład powtarzanie ostatniej wartości, długość prognozy i błąd dla pustej historii.

    Test sprawdza właśnie te wymagania. Wystarczy kilka wymyślonych liczb i wynik obliczony ręcznie. Nie musisz wczytywać całego zbioru sprzedaży.

    To inne sprawdzenie niż ocena trafności prognozy. Trafność mierzyliśmy w labie 03 za pomocą MAE na odłożonym okresie. Do niej wrócimy w module 08. Test kodu odpowiada teraz na pytanie: czy po zmianie funkcja nadal zachowuje się zgodnie z opisem?

    Po co testy

    Test to mały program, który wywołuje Twój kod na znanych danych i porównuje wynik z oczekiwaniem. Opisuje wymaganie w postaci, którą da się uruchomić.

    Przydaje się szczególnie po zmianach. Jeśli zmodyfikujesz fit, testy pomogą wykryć, czy naruszyłeś sprawdzane wcześniej zachowania.

    Dobry test ma trzy części, oddzielone pustą linią:

    def test_seasonal_naive_repeats_the_last_season() -> None:
    history = [1.0, 2.0, 3.0, 10.0, 20.0, 30.0]                                  # przygotuj

    forecast = SeasonalNaiveForecaster(season=3).fit(history).predict(horizon=3)  # wykonaj

    assert forecast == [10.0, 20.0, 30.0]                                       # sprawdź

    Nadaj testowi nazwę opisującą sprawdzane zachowanie. Gdy się nie powiedzie, nazwa pomoże znaleźć problem. Dane powinny być małe i widoczne w teście, a oczekiwany wynik ustalony niezależnie od sprawdzanej funkcji. To reguła T2.

    pytest

    pytest sam znajduje testy: pliki test_*.py, a w nich funkcje test_* i metody test_* w klasach Test*. Asercją jest zwykłe assert. Gdy nie przejdzie, pytest pokazuje obie strony porównania:

    $ uv run pytest -q
F                                                                        [100%]
=================================== FAILURES ===================================
______________________ test_naive_repeats_the_last_value _______________________

    def test_naive_repeats_the_last_value() -> None:
        forecast = predict([3.0, 5.0, 4.0], horizon=2)

>       assert forecast == [4.0, 4.0]
E       assert [3.0, 3.0] == [4.0, 4.0]
E
E         At index 0 diff: 3.0 != 4.0

    Kod zwrócił pierwszą wartość historii zamiast ostatniej. Nie trzeba niczego dopisywać, żeby to zobaczyć.

    Plik tests/models/test_local.py zawiera poniższe nazwy. Które pytest uruchomi jako testy? Zaznacz wszystkie.
    • def test_naive_repeats_the_last_value()Tak: funkcja z prefiksem test_ w pliku test_*.py.
    • def check_naive()Bez prefiksu test_ to zwykła funkcja pomocnicza.
    • class TestSeasonal: z metodą def test_wraps(self)Tak: metoda test_* w klasie Test*.
    • def _test_helper()Nazwa zaczyna się od podkreślnika, nie od test_.

    Błędy i liczby zmiennoprzecinkowe

    Sprawdź również, co funkcja robi z niepoprawnymi danymi. Jest to część jej opisu działania, uwzględniona w regule T3. Funkcja pytest.raises sprawdza typ zgłoszonego wyjątku, a argument match pozwala sprawdzić jego komunikat:

    def test_fit_rejects_an_empty_history() -> None:
    with pytest.raises(ValueError, match="empty"):
        NaiveForecaster().fit([])

    Bez match test może przejść również wtedy, gdy ValueError wystąpił z innego powodu. Sprawdzenie komunikatu pomaga odróżnić oczekiwane odrzucenie danych od innego błędu.

    import math

print(0.1 + 0.2 == 0.3, math.isclose(0.1 + 0.2, 0.3))
    • True TrueUłamki dziesiętne jak 0.1 nie mają dokładnej postaci binarnej. Suma różni się od 0.3 na siedemnastym miejscu.
    • False TrueTak. Porównanie dokładne zawodzi, porównanie z tolerancją nie. W testach tę rolę gra pytest.approx: assert forecast == pytest.approx([2.0, 2.0]).
    • False Falsemath.isclose porównuje z małą względną tolerancją, więc taka różnica mu nie przeszkadza.

    Parametryzacja

    Ten sam test dla kilku danych nie wymaga kopiowania. @pytest.mark.parametrize uruchamia go osobno dla każdego zestawu:

    @pytest.mark.parametrize(
    "forecaster",
    [NaiveForecaster(), SeasonalNaiveForecaster(season=2), MovingAverageForecaster()],
)
@pytest.mark.parametrize("horizon", [1, 4])
def test_forecast_has_one_value_per_step(forecaster: LocalForecaster, horizon: int) -> None:
    forecast = forecaster.fit([1.0, 2.0, 3.0]).predict(horizon=horizon)

    assert len(forecast) == horizon
    Ile testów uruchomi pytest z tej jednej funkcji?
    • 1Każdy zestaw parametrów to osobny test z osobnym wynikiem w raporcie.
    • 5Dwa dekoratory nie dodają się, tylko mnożą: każdy model z każdym horyzontem.
    • 6Tak. Trzy modele razy dwa horyzonty. Jeśli jedna próba się nie powiedzie, raport wskaże model i horyzont.

    Fixtures

    Fixture to funkcja przygotowująca dane lub zasób potrzebny w teście. Żeby otrzymać jej wynik, podajesz nazwę fixture jako parametr testu. Wbudowane tmp_path udostępnia na przykład osobny katalog tymczasowy dla każdego testu.

    @pytest.fixture
def weekly_history() -> list[float]:
    return [5.0, 3.0, 3.0, 4.0, 6.0, 9.0, 8.0] * 2


def test_seasonal_repeats_the_week(weekly_history: list[float]) -> None:
    forecast = SeasonalNaiveForecaster(season=7).fit(weekly_history).predict(7)

    assert forecast == weekly_history[-7:]


def test_summary_is_written(tmp_path: Path) -> None:
    path = save_summary({"A": {"total": 1.0}}, tmp_path / "out" / "summary.json")

    assert path.exists()

    Fixture wspólną dla wielu plików kładzie się do tests/conftest.py. pytest czyta ten plik sam, bez importu.

    Test bez sieci, zegara i przypadku

    Jeśli test bez zmiany kodu raz przechodzi, a raz się nie udaje, trudno zaufać jego wynikowi. Przyczyną bywa sieć, bieżąca data, losowość bez ustalonego ziarna lub kolejność testów. Reguła T4 wymaga uniezależnienia testów od takich czynników. Zacznij od najprostszego sposobu:

    1. Parametr. Zamiast wyznaczać datę wewnątrz funkcji przez date.today(), pozwól przekazać ją jako today. Test poda wtedy stałą datę. Nazywamy to wstrzykiwaniem zależności: funkcja otrzymuje z zewnątrz coś, od czego zależy jej wynik.
    2. monkeypatch. Wbudowana fixture pytest, która na czas testu podmienia atrybut, zmienną środowiskową albo słownik, a po teście przywraca oryginał: 
      def test_reads_the_bucket_from_the_environment(monkeypatch: pytest.MonkeyPatch) -> None:
    monkeypatch.setenv("DATA_BUCKET", "test-bucket")

    assert load_settings().bucket == "test-bucket"
    3. Mock. Obiekt z unittest.mock, któremu ustawiasz zwracane wartości. Zapamiętuje wywołania, co pozwala później sprawdzić ich liczbę i argumenty.
    from unittest.mock import Mock

storage = Mock()
storage.load.return_value = [1.0, 2.0]

print(storage.load("x.parquet"), storage.load.call_count, storage.save.called)
    • [1.0, 2.0] 1 AttributeErrorMock tworzy każdy atrybut przy pierwszym dostępie, także save, którego nikt nie ustawił.
    • [1.0, 2.0] 1 FalseTak. load zwraca ustawioną wartość i liczy wywołania. save istnieje, ale nikt go nie wołał.
    • None 1 Falsereturn_value ustawia, co zwraca wywołanie load(...).
    Pułapka

    Zwykły Mock może zaakceptować także nieistniejącą metodę, na przykład literówkę storage.laod(). Test z takim obiektem nie musi więc wykryć niezgodności z prawdziwą biblioteką.

    Jeśli to możliwe, użyj rzeczywistego obiektu na małych danych. Gdy potrzebna jest usługa zewnętrzna, możesz skorzystać z jej lokalnego odpowiednika do testów, takiego jak moto dla S3 w module 15.

    Czy test coś chroni

    Przechodzący test nie mówi jeszcze, jakie błędy potrafi wykryć. Możesz to sprawdzić, celowo zmieniając kod.

    Załóżmy, że zastąpisz history[-1] przez history[0]. Jeśli wszystkie testy nadal przechodzą, nie rozróżniają użycia pierwszej i ostatniej wartości w prognozie naiwnej.

    Na tym polega testowanie mutacyjne. W sprawdzeniu 04.2 Twoje testy zostaną uruchomione na ośmiu zmienionych wersjach kodu. Każda zawiera jeden typowy błąd. Jeśli testy zaakceptują taką wersję, oznacza to, że tego błędu nie wykrywają.

    Test: assert len(NaiveForecaster().fit([1.0, 1.0, 1.0]).predict(3)) == 3. Który błąd wykryje?
    • Powtarzanie pierwszej wartości zamiast ostatniej.Historia ma same jedynki: pierwsza i ostatnia są równe. Poza tym test sprawdza tylko długość.
    • predict zwraca o jedną wartość za dużo.Tak. Tylko tyle. Dobór danych decyduje, co test w ogóle może zobaczyć.
    • Oba.Przy historii samych jedynek pierwsza wartość jest równa ostatniej.

    Dobieraj dane tak, żeby poprawny i błędny kod dawały różne wyniki. Lista [3.0, 5.0, 4.0] pozwala rozróżnić pierwszą, środkową i ostatnią wartość. Lista [1.0, 1.0, 1.0] nie wykryje zamiany jednej z tych pozycji na inną.

    Pakiet

    Pakiet to katalog z plikiem __init__.py, który da się zaimportować. Żeby zaimportować go z każdego miejsca, instaluje się go w środowisku. Kurs ma taki układ:

    mle-course/
├── pyproject.toml      opis projektu i zależności
├── uv.lock             dokładne wersje wszystkich pakietów
├── src/
│   └── freshcast/      Twój pakiet
│       ├── __init__.py
│       └── models/
│           ├── __init__.py
│           └── local.py
└── tests/
    └── models/
        └── test_local.py

    Kod leży w src/, a nie w katalogu głównym. Dzięki temu import freshcast nie znajdzie kodu przypadkiem w bieżącym katalogu. Znajdzie tylko wersję zainstalowaną w środowisku. Testy sprawdzają więc to samo, co dostanie każdy, kto zainstaluje pakiet.

    uv sync instaluje projekt w trybie edytowalnym. Środowisko nie trzyma kopii kodu, tylko wskazanie na src/. Zmiana w pliku jest od razu widoczna, bez reinstalacji.

    pyproject.toml

    [project]
name = "mle-course"
requires-python = ">=3.12,<3.13"
dependencies = [          # potrzebne do działania
    "pandas>=3.0,<4",
    "lightgbm>=4.5",
]

[dependency-groups]
dev = [                   # potrzebne tylko przy pracy nad kodem
    "pytest>=8.3",
    "ruff>=0.8",
]

[project.scripts]
course = "coursekit.cli:main"   # polecenie `course` wywołuje tę funkcję

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

    Zapis pandas>=3.0,<4 to zakres: każda wersja od 3.0 w górę, poniżej 4. Zakres mówi, z czym kod ma działać. Nie mówi, która wersja jest zainstalowana. To zapisuje plik lock.

    uv.lock

    Plik uv.lock zapisuje dokładne wersje pakietów, ich zależności i sumy kontrolne. Pozwala odtworzyć uzgodniony zestaw bibliotek na komputerze, w CI i w obrazie Dockera. Dodaj go do gita. Zmiany w nim wprowadzaj narzędziem uv, zamiast edytować go ręcznie.

    PolecenieRobi
    uv add polarsdopisuje zależność do pyproject.toml, odświeża lock, instaluje
    uv add --dev pytestto samo w grupie dev
    uv lockprzelicza lock z pyproject.toml
    uv syncdoprowadza środowisko do stanu z locka
    uv run polecenieuruchamia w środowisku projektu, najpierw synchronizując
    Kolega usuwa uv.lock z repozytorium: "przecież zależności są w pyproject.toml". Co tracicie?
    • Nic, uv sync odtworzy to samo.Odtworzy najnowsze wersje pasujące do zakresów w dniu instalacji. Za miesiąc mogą być inne.
    • Powtarzalność: dwie instalacje w różnych dniach mogą dać różne wersje pakietów.Tak. Model, który wczoraj dawał jeden wynik, jutro może dać inny tylko dlatego, że wyszła nowa wersja zależności.
    • Listę zależności deweloperskich.Grupy zależności są w pyproject.toml. Lock zapisuje tylko ich dokładne wersje.

    W innych projektach możesz spotkać Poetry. Ono również korzysta z pyproject.toml, pliku lock i osobnego środowiska projektu. W labie zbudujesz ten sam pakiet obydwoma narzędziami i porównasz sposób pracy.

    Reguła

    Od tego modułu każda publiczna funkcja pakietu powinna mieć test, zgodnie z regułą T1. Przed zgłoszeniem kodu do przeglądu uruchom lokalnie ruff, mypy, pytest i course check. Wszystkie muszą przejść. To warunek reguły G3.

    Ćwiczenia

    Test, który łapie błąd

    Napisz test funkcji moving_average. Sprawdzenie uruchomi go najpierw na poprawnej implementacji, a potem na dwóch wersjach z błędem. Twój test ma zaakceptować pierwszą i wykryć błąd w każdej z dwóch pozostałych.

    Tytuł raportu bez zegara

    Funkcja poniżej korzysta z bieżącej daty, więc jej wynik zależy od dnia uruchomienia. Dodaj opcjonalny argument today, żeby w teście można było przekazać stałą datę. Gdy argument zostanie pominięty, funkcja ma działać jak wcześniej.
