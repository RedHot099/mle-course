    B7.2 · Ścieżka A–F

    Pierwszy branch, commit i pull request

    Funkcja i testy już działają lokalnie. Teraz zapiszesz ich historię w gicie i pokażesz zmianę w pull requeście. Skorzystasz też z gotowej konfiguracji, która uruchomi sprawdzenia na GitHub.

    • Przed lekcją: B7.1, konto GitHub oraz git. W razie braku konta możesz najpierw wykonać lokalne sprawdzenia.
    • Jak pracować: przewiduj wyniki, uruchamiaj kod i wyjaśniaj to, co widzisz

    Zapisz konkretną zmianę

    Git zapisuje historię zmian w plikach. Projekt, dla którego prowadzisz taką historię, nazywamy repozytorium. Commit jest zapisem wybranych zmian.

    Branch, czyli gałąź, pozwala pracować nad zmianą osobno od wersji bazowej projektu. Gdy chcesz pokazać swoją pracę do przeglądu, otwierasz pull request. Pokazuje on różnice między Twoją gałęzią a gałęzią, do której zmiana ma trafić.

    Użyj małego projektu z poprzedniej lekcji. Jego pierwsze CI sprawdzi tylko Twoją funkcję i testy. Pracuj na własnej kopii repozytorium kursu, w nowej gałęzi. Mały projekt practice ma własne zależności, ale nie osobne zagnieżdżone repozytorium Git.

    Przygotuj git i dostęp do GitHub

    W terminalu sprawdź git --version. Jeśli polecenie jest niedostępne, zainstaluj Git na swoim komputerze według instrukcji GitHub: Set up Git dla swojego systemu.

    Przed pierwszym commitem ustaw autora: git config --global user.name "Twoje imię" oraz git config --global user.email "adres przypisany do konta GitHub". Podstaw własne dane. Adres pojawi się w historii commitów; możesz użyć prywatnego adresu noreply z ustawień GitHub.

    Git przechowuje historię lokalnie. GitHub jest usługą, do której wyślesz wybrane zmiany. Utwórz konto i zaloguj się w przeglądarce. Do pracy przez HTTPS użyj sposobu logowania z podlinkowanej instrukcji. Jeśli korzystasz z zainstalowanego GitHub CLI, polecenie gh auth login prowadzi przez logowanie do GitHub.com i autoryzację przez przeglądarkę. Nie zapisuj tokenów w plikach projektu ani w adresie origin.

    Jeśli dostęp do konta lub instalacja są chwilowo niemożliwe, zachowaj projekt i wyniki testów lokalnie. Do wysyłania zmian wrócisz po rozwiązaniu problemu.

    Własna gałąź i te same pliki

    W labie B7.1–B7.2 sprawdzisz istniejącą historię repozytorium, utworzysz gałąź learning/summary i zapiszesz wybrane pliki z practice. Nie kopiuj funkcji do nowego klonu. Lab podaje kompletną sekwencję poleceń.

    Przeczytaj zmianę przed zapisem

    git status pokazuje zmienione i nowe pliki. git add wybiera zmiany do następnego commita, a git diff --cached pokazuje, co dokładnie zostanie zapisane. Przed commitem sprawdź cały ten widok, także pliki wybrane wcześniej. Nie dodawaj środowiska .venv, kopii zapasowej funkcji ani wygenerowanych wyników.

    Skorzystaj z gotowego sprawdzania

    Po otwarciu lub aktualizacji pull requesta GitHub może uruchomić testy i inne sprawdzenia na osobnym komputerze. Takie automatyczne sprawdzanie zmian nazywamy CI.

    Utwórz folder .github/workflows i umieść w nim przygotowany plik checks.yml. Workflow pracuje w folderze practice i sprawdza tylko ten mały projekt. Nie musisz pisać konfiguracji od początku.

    git add .github/workflows/checks.yml
git diff --cached
git commit -m "Run checks for pull requests"
git push -u origin learning/summary

    Na GitHub wybierz Compare & pull request. Jako bazę ustaw main, a jako źródło learning/summary. W opisie napisz, co oblicza funkcja i jakie wymagania sprawdzają testy. W zakładce Checks znajdziesz wyniki CI. Jeśli krok się nie powiedzie, odczytaj polecenie i komunikat błędu, a potem uruchom to polecenie lokalnie.

    Jeśli GitHub Actions są niedostępne dla Twojego konta lub repozytorium, wykonaj lokalne sprawdzenia. Możesz kontynuować naukę bez zakupu usługi. Gdy CI zadziała, wyjaśnij, jakie sprawdzenia wykonało.

    Przeczytaj zmianę tak, jakby napisał ją ktoś inny

    Obejrzyj różnice w kodzie. Czy funkcja uwzględnia zera? Co robi, gdy nie ma znanych pomiarów? Czy pozostawia listę bez zmian? Do każdego pytania znajdź test, który wykryłby niepoprawne zachowanie.

    Standard kursu zbiera zasady, do których wracamy przy przeglądzie kodu. Tutaj wykorzystaj K2 (opis działania), K4 (konkretny wyjątek), K9 (formatowanie i lint), T2 (małe, jawne dane), T3 (przypadki brzegowe) oraz G4 (ochrona danych prywatnych i sekretów).

    Masz teraz mały moduł, testy i zapisane polecenia, które pozwalają powtórzyć sprawdzenia. Możesz przejść do dalszej nauki. Kolejne reguły standardu wprowadzimy wraz z narzędziami, do których się odnoszą.

    Co zapisuje commit?

    • Wszystko z całego dyskuGit nie zapisuje plików spoza repozytorium i nie wybiera automatycznie wszystkich zmian.
    • Wynik ostatniej komórki notebooka z pamięciPamięć kernela nie jest historią plików w git.
    • Wybrane przez git add zmianyDlatego przed zapisem czytasz git diff --cached.

    Sprawdź, co pamiętasz

    Wyjaśnij komuś innemu różnicę między testem, commitem i CI.

    Sprawdź własne wyjaśnienie

    Test sprawdza zachowanie kodu na określonych danych. Commit zapisuje wybrane zmiany w plikach. CI wykonuje uzgodnione sprawdzenia na innym komputerze. Wyjaśnij na swoim projekcie, czego zabrakłoby w Twojej pracy bez każdej z tych czynności.
