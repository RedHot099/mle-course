    B7.2 · Ścieżka A i B

    Pierwszy branch, commit i pull request

    Przygotujesz małą zmianę z własną funkcją i testami oraz przeczytasz wynik gotowego CI.

    • Przed lekcją: B7.1, konto GitHub oraz git. W razie braku konta możesz najpierw wykonać lokalne sprawdzenia.
    • Tryb: najpierw przewidź, potem wykonaj i wyjaśnij

    Zapisz konkretną zmianę

    Git zapisuje historię wersji. Repozytorium to projekt z tą historią. Branch jest nazwą linii pracy. Commit zapisuje wybrany stan zmian. Pull request pokazuje różnicę między Twoją gałęzią a bazą i pozwala poprosić o review.

    Pracujesz na własnym małym projekcie, nie na gałęzi kursu. Nie kopiujesz całego mle-course do nowego repozytorium. Dzięki temu pierwsze CI sprawdza tylko to, co już napisałeś.

    Jeśli brakuje git lub logowania GitHub, skorzystaj z odpowiednich kroków konfiguracji git i logowania. Instalacja wymagana w tych krokach jest czynnością na Twoim komputerze. Konto i zdalny PR nie są warunkiem dalszej nauki pojęć ML.

    Najpierw baza repozytorium

    1. Na GitHub utwórz własne repozytorium ml-basics. Dodaj README podczas tworzenia, aby powstała baza main.
    2. Na stronie repozytorium skopiuj adres HTTPS z przycisku Code.
    3. W terminalu sklonuj je do nowego folderu i utwórz gałąź. W adresie poniżej zastąp YOUR_LOGIN własnym loginem.
    git clone https://github.com/YOUR_LOGIN/ml-basics.git ~/mle-practice-review
cd ~/mle-practice-review
git switch -c learning/summary
git status

    Git status powinien pokazywać gałąź learning/summary. Jeśli klonowanie lub logowanie nie działa, zachowaj swój projekt lokalnie. To blokada dostępu, a nie błąd funkcji.

    Wybierz pliki przed commitem

    Z katalogu mle-practice skopiuj do mle-practice-review wyłącznie własne summary.py, test_summary.py, pyproject.toml, .python-version i uv.lock. Uzupełnij README nowego repozytorium instrukcją testów. Dodaj gotowy .gitignore pod nazwą .gitignore. Nie przenoś .venv, pomiarów ani wyników notebooka.

    uv sync --locked
uv run pytest -q
uv run ruff format --check summary.py test_summary.py
uv run ruff check summary.py test_summary.py
uv run mypy --disallow-untyped-defs summary.py
git diff

    Git diff pokazuje różnice w plikach śledzonych. Nowe pliki zobaczysz też w git status. Nie używaj tu git add .; wybierz pliki jawnie i przeczytaj przygotowaną zmianę.

    git add summary.py test_summary.py pyproject.toml .python-version uv.lock README.md .gitignore
git diff --cached
git commit -m "Add observation summary with tests"

    Git add wybiera zmiany do następnego zapisu. Git diff --cached pokazuje właśnie ten wybór. Przed commitem sprawdź, że nie ma haseł, kluczy, danych i .venv. Commit mówi, co zmieniasz, w trybie rozkazującym.

    Skorzystaj z gotowego sprawdzania

    CI uruchamia sprawdzenia na innym komputerze. Nie wdraża aplikacji. W nowym repozytorium utwórz katalog .github/workflows i zapisz w nim gotowy checks.yml. Ten plik jest dostarczonym narzędziem, nie zadaniem pisania workflow od zera.

    git add .github/workflows/checks.yml
git diff --cached
git commit -m "Run checks for pull requests"
git push -u origin learning/summary

    Na GitHub wybierz Compare & pull request. Baza ma być main, źródło learning/summary. W opisie napisz, co oblicza funkcja i co sprawdzają testy. Otwórz zakładkę Checks. Jeśli krok jest czerwony, przeczytaj nazwę polecenia i ostatni komunikat, a potem odtwórz je lokalnie.

    Jeśli Actions są wyłączone dla Twojego konta lub repozytorium, zapisz ograniczenie i zachowaj lokalne wyniki. Nie kupuj usługi, żeby zaliczyć tę lekcję. Zrzut ekranu z zielonym CI nie zastępuje wyjaśnienia testów.

    Sprawdź własną zmianę jak czytelnik

    Przejdź po diffie i odpowiedz: czy funkcja zachowuje zera, czy jawnie odrzuca brak danych, czy nie zmienia wejścia, czy testy sprawdzają tę umowę? Oznacz reguły z standardu: K2 opis zachowania, K4 konkretny wyjątek, K9 format i lint, T2 małe jawne dane, T3 przypadki brzegowe oraz G4 brak danych i sekretów w repozytorium.

    Nowa ścieżka wprowadza reguły w swoim tempie. Nie wymagamy tu standardu modułów, których jeszcze nie robiłeś. Po B potrafisz pokazać własny mały moduł z testami; nie potrzebujesz Docker, rozbudowanego pakietu ani implementacji dekoratora.

    Co zapisuje commit?

    • Wszystko z całego dyskuGit nie zapisuje plików spoza repozytorium i nie wybiera automatycznie wszystkich zmian.
    • Wynik ostatniej komórki notebooka z pamięciPamięć kernela nie jest historią plików w git.
    • Wybrane przez git add zmianyDlatego przed zapisem czytasz git diff --cached.

    Powrót bez zaglądania

    Wyjaśnij komuś innemu różnicę między testem, commitem i CI.

    Sprawdź własne wyjaśnienie

    Test sprawdza zachowanie. Commit zapisuje wybrany stan plików. CI wykonuje umówione sprawdzenia poza Twoim komputerem. Każda z tych czynności rozwiązuje inny problem.
