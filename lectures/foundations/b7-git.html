    Pierwszy branch, commit i pull request

    Zapisz własną funkcję i testy na nowej gałęzi. Otwórz pull request i sprawdź, czy dostarczone CI potrafi powtórzyć Twoje lokalne sprawdzenia.

    • Przed lekcją: B7.1, konto GitHub oraz git. W razie braku konta możesz najpierw wykonać lokalne sprawdzenia.
    • Tryb: najpierw przewidź, potem wykonaj i wyjaśnij

    Zapisz konkretną zmianę

    Git zapisuje historię plików projektu. Projekt z taką historią to repozytorium. Branch, czyli gałąź, pozwala prowadzić pracę oddzielnie od wersji bazowej. Commit zapisuje wybrane zmiany. Pull request pokazuje różnicę między gałęziami i służy do przeglądu zmian przed ich połączeniem.

    Użyj małego projektu z poprzedniej lekcji. Jego pierwsze CI sprawdzi tylko Twoją funkcję i testy. Repozytorium całego kursu zostaw osobno.

    Jeśli git nie jest gotowy albo nie możesz zalogować się do GitHub, skorzystaj z instrukcji konfiguracji git i logowania. W razie problemów zachowaj projekt i wyniki testów lokalnie. Do ćwiczenia współpracy możesz wrócić po uzyskaniu dostępu.

    Najpierw baza repozytorium

    1. Na GitHub utwórz własne repozytorium ml-basics. Dodaj README podczas tworzenia, aby powstała baza main.
    2. Na stronie repozytorium skopiuj adres HTTPS z przycisku Code.
    3. W terminalu sklonuj je do nowego folderu i utwórz gałąź. W adresie poniżej zastąp YOUR_LOGIN własnym loginem.
    git clone https://github.com/YOUR_LOGIN/ml-basics.git ~/mle-practice-review
cd ~/mle-practice-review
git switch -c learning/summary
git status

    git status powinien pokazać gałąź learning/summary. Jeśli klonowanie się nie udało, wyjaśnij problem z adresem lub dostępem, zanim przejdziesz do kolejnych poleceń. Twoja funkcja i testy pozostają w folderze mle-practice.

    Wybierz pliki przed commitem

    Z folderu mle-practice skopiuj do mle-practice-review pliki summary.py, test_summary.py, pyproject.toml, .python-version i uv.lock. Uzupełnij README instrukcją testów. Zapisz przygotowany plik wykluczeń jako .gitignore. Środowisko .venv odtworzysz poleceniem uv sync, więc nie kopiuj tego folderu.

    uv sync --locked
uv run pytest -q
uv run ruff format --check summary.py test_summary.py
uv run ruff check summary.py test_summary.py
uv run mypy --disallow-untyped-defs summary.py
git diff

    git diff pokazuje zmiany w plikach już śledzonych przez git. Nowe pliki zobaczysz w git status. Wybierz pliki do zapisu przez git add, a potem przeczytaj przygotowaną zmianę:

    git add summary.py test_summary.py pyproject.toml .python-version uv.lock README.md .gitignore
git diff --cached
git commit -m "Add observation summary with tests"

    git add wybiera zmiany do następnego commita. git diff --cached pozwala je przeczytać przed zapisem. Sprawdź zwłaszcza, czy nie wybrałeś danych, haseł, kluczy ani folderu .venv. Komunikat commita krótko opisuje zmianę, tutaj: dodanie podsumowania obserwacji wraz z testami.

    Skorzystaj z gotowego sprawdzania

    CI uruchamia sprawdzenia projektu na innym komputerze po otwarciu lub aktualizacji pull requesta. Utwórz folder .github/workflows i zapisz w nim gotowy plik checks.yml. W tej lekcji korzystasz z przygotowanej konfiguracji.

    git add .github/workflows/checks.yml
git diff --cached
git commit -m "Run checks for pull requests"
git push -u origin learning/summary

    Na GitHub wybierz Compare & pull request. Jako bazę ustaw main, a jako źródło learning/summary. W opisie napisz, co oblicza funkcja i jakie wymagania sprawdzają testy. W zakładce Checks znajdziesz wyniki CI. Jeśli krok się nie powiedzie, odczytaj polecenie i komunikat błędu, a potem uruchom to polecenie lokalnie.

    Jeśli GitHub Actions są niedostępne dla Twojego konta lub repozytorium, zapisz to ograniczenie i zachowaj wyniki lokalnych sprawdzeń. Możesz kontynuować naukę bez zakupu usługi. Gdy CI zadziała, wyjaśnij, jakie sprawdzenia wykonało.

    Sprawdź własną zmianę jak czytelnik

    Przeczytaj diff tak, jakbyś widział kod po raz pierwszy. Czy funkcja zachowuje zera? Co robi bez znanych pomiarów? Czy zmienia wejście? Który test zauważyłby każde z tych naruszeń? Powiąż uwagi z regułami standardu: K2 opis zachowania, K4 konkretny wyjątek, K9 format i lint, T2 małe jawne dane, T3 przypadki brzegowe, G4 brak danych i sekretów w repozytorium.

    Na końcu B masz mały moduł, testy i sposób powtórzenia sprawdzeń. To wystarczy do kolejnego etapu nauki. Reguły dotyczące późniejszych modułów będziemy stosować wtedy, gdy poznasz potrzebne narzędzia.

    Co zapisuje commit?

    • Wszystko z całego dyskuGit nie zapisuje plików spoza repozytorium i nie wybiera automatycznie wszystkich zmian.
    • Wynik ostatniej komórki notebooka z pamięciPamięć kernela nie jest historią plików w git.
    • Wybrane przez git add zmianyDlatego przed zapisem czytasz git diff --cached.

    Sprawdź własne wyjaśnienie

    Test sprawdza zachowanie kodu na określonych danych. Commit zapisuje wybrane zmiany w plikach. CI wykonuje uzgodnione sprawdzenia na innym komputerze. Wyjaśnij na swoim projekcie, co straciłbyś bez każdej z tych czynności.
